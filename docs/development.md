# 开发约定

## Git

- 本 fork 直接在 `main` 上开发、提交并推送，不创建开发分支。
- 提交信息用中文，小批次，一个提交表达一个清楚的变更目的。
- 提交和发布前运行下面的检查，并审阅本次 diff：核对范围、文档、秘密和未实现的内容。
- 改版版本使用 `X.Y.Z-mod`，Git 标签和镜像标签使用同一版本；发布到本 fork 的 Releases 与 GHCR。

## 代码与依赖

优先使用成熟组件，业务胶水保持直接可读。不为假想的扩展建立层层接口，不为开发中的短命错误保留兼容兜底。一个问题反复打补丁仍不稳定时，回到全局设计重新考虑。

取舍原则见[架构](architecture.md#取舍原则)：按实际发生的概率、后果和实现与运维成本决定投入，先简单可用，出现具体问题再加必要的措施。

代码组织：一个文件一个职责，入口文件（`server.ts`、`App.tsx`）只做编排和分发，具体处理放具名函数或所属模块；同一段逻辑出现第二次就提取，但不为只有一处使用的代码预留抽象。协议里的事件类型从 `@cc-desk-tunnel/protocol` 引用具名类型。注释写约束和原因，不复述代码；模块结构见各模块 README，改动结构时同步更新。

三个 npm workspace 共享根目录的 `package-lock.json`，用 `npm ci` 复现依赖，不引入第二种包管理器。Node 24 直接运行可擦除的 TypeScript，`npm run typecheck` 仍是必须的静态检查。第三方二进制的下载来源、版本和校验值写在使用它的脚本里。不提交依赖目录、构建产物或凭据。

Windows 上的 shell 命令与脚本使用 `pwsh.exe`（PowerShell 7）。终端、管道、子进程和文本文件一律 UTF-8。

## 文档

- `README.md` 是总览、快速开始和文档索引。
- 跨模块的说明放 `docs/`，模块细节跟随模块目录。
- 工作清单、核对过程放在被忽略的 `.local/`，收尾清理；文档只保留功能说明、必要取舍和待验证事项。
- 区分已验证的事实与尚未验证的实现，后者记在[路线](roadmap.md)。
- 过时的内容直接删除或改写，不在旁边追加“已过时”的说明；历史由 Git 保留。

## 发布

版本号以 `apps/desktop/package.json` 为准，两端共用；[变更记录](../CHANGELOG.md)里要有同名的一节，按该文件开头说明的结构书写（一句概括，然后是新增功能、优化改进、问题修复、升级说明）。发布脚本把这一节放进固定的发布说明模板：项目简介、本版变化、下载与升级，因此每一版的发布页读起来是同一个样子。

1. 在 `main` 改好 `X.Y.Z-mod` 版本号与变更记录，通过检查后提交并用现有 Git 凭据推送。
2. 创建并推送相同提交的 `vX.Y.Z-mod` 标签：`git tag vX.Y.Z-mod`，然后 `git push origin vX.Y.Z-mod`。
3. 标签触发 `package` 工作流：先建草稿，再构建所有客户端、服务端和 amd64/arm64 镜像。所有构建、启动检查、文件清单和哈希都通过后自动公开 Release，并更新镜像 `latest`。失败时保留草稿，不发布不完整版本。

这个 Git 标签发布入口不要求本机 GitHub CLI 登录。工作流使用仓库自动下发的 `GITHUB_TOKEN`，不把个人凭据放进代码。仍可用 `npm run release -- --dry-run` 离线生成说明；原有 `gh` 手动发布入口也保留。

发布的文件只来自 GitHub 的机器：谁来发布、在哪台电脑上发布，得到的都是同一提交按同一流程构建的文件，构建记录留在该次运行里。

服务端镜像也在这一步发布，不需要另外操作：`package` 调用 `images.yml`，在 GitHub 的 x86_64 和 arm64 机器上各自构建、跑完部署测试（`deploy/test.sh`、`deploy/test-image.sh`）后推送，合成一个双架构标签 `ghcr.io/power12317/cc-desk-tunnel:X.Y.Z`。镜像没有打出或测试没过，草稿同样不会挂上文件。已经存在的版本标签不会被覆盖：重跑时只核对它属于同一提交。正式发布（或把预发布转正）后，`image-latest.yml` 把 `latest` 指向 GitHub 显示为 Latest 的版本；部署脚本只按版本号拉取，不依赖 `latest`。

GHCR 上的包已设为公开，部署时不需要登录；`images` 推送后会匿名检查一次，万一哪天变成私有会在这里失败。手动运行 `images` 时，标签留空只构建和测试，填 `verify-名称` 会推送一个测试用的镜像，不影响正式版本。

`release.json` 里的 `runtime` 是该版本所需的镜像级别，取自 `deploy/docker/runtime-level`。改动 Dockerfile、镜像入口脚本或 Node.js 的版本时把这个数字加一：旧镜像上的服务端会提示在服务器上升级，而不是自行安装。只更换 Claude Code 的版本不需要加，升级时会把所需版本装进数据目录。

发布在此时才打上 `v<版本>` 标签。已发布的版本不改文件，有问题就递增版本重新发布。

不在本机构建时，GitHub 上的 `package` 工作流可以代为打出 Windows 安装包、两种架构的 macOS 安装包、Linux 的 deb、四个系统的终端客户端包（`npm run package:cli`，在哪个系统上运行就打哪个系统的）与服务端程序包：在 Actions 页手动运行，或在 `dev/**` 分支上改动打包脚本时自动运行；文件随该次运行保留 3 天，不签名；只有发布脚本启动的那一次会把文件挂到草稿发布上。

新版本先作为预发布放出：`npm run release -- --publish --prerelease`。预发布不标记为 Latest，服务端不会把它当作更新提供，安装脚本的下载入口也仍指向上一个正式版，试用的人从发布页手动下载两端的文件。确认没有问题后在发布页取消“预发布”并设为 Latest，它就成为正式版。发布说明从一开始就按正式版书写，转正时不改一个字，文件也不重新构建。

## 凭据与本机文件

开发用的服务器地址、账号、令牌等只放在被忽略的 `.local/`，不进入版本库、日志或文档。一次性的人工测试入口和与具体机器相关的脚本也放在那里；可复用的回归测试才提交。

## 提交前检查

```sh
npm run check
npm run typecheck
npm run format:check
npm test
git diff --check
```

`npm run check` 检查的是 Git 索引，新增文件要先暂存；它只识别少数秘密特征，不是专业的秘密扫描器。涉及界面行为时运行 `npm run test:ui`（先 `npm run setup:desktop`，并安装 Playwright 浏览器或设置 `PLAYWRIGHT_CHANNEL=chrome`）。模拟服务上的测试结果与真实 Claude 的验证分别记录，不能互相替代。
