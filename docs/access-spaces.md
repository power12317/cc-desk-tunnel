# 按服务访问密钥划分空间

此功能适用于现有 Linux Docker/Compose、Linux 原生及 macOS 原生服务。Windows、macOS、Linux 客户端以及 Web/手机浏览器共用服务端授权逻辑。服务访问密钥与 Claude 登录、SSH 临时密钥互相独立，不需要多个 Claude 账号。

## 配置与轮换

原有 `PROXY_TOKEN` 继续有效，对应稳定空间 ID `default`。新增 `PROXY_ACCESS_KEYS_FILE` 指向本机私有 UTF-8 JSON 文件，格式如下（示意秘密必须替换为本机随机生成的值）：

```json
[
  { "id": "team-a", "token": "replace-with-random-secret-at-least-24-characters" },
  { "id": "team-b", "token": "replace-with-another-random-secret-at-least-24-characters" }
]
```

ID 是管理员指定的稳定标识，允许 1–64 位英文字母、数字、下划线、连字符，首位必须是字母或数字。每条秘密至少 24 字符且不能有首尾空格。禁止同一秘密重复配置。文件权限应为 0600，父目录 0700；不要提交、输出或发送真实秘密。配置无效时拒绝启动，错误不包含秘密内容。

可以保留原 `PROXY_TOKEN` 并新增其他空间，也可以只用 JSON 文件。多条不同秘密可指向同一 ID，用于同空间的凭据轮换。更换 token 时保持 ID，空间及原生 cwd 不变；修改 ID 表示新空间。配置在启动时载入，维护窗口重启生效，旧连接随旧服务结束。浏览器会话同时绑定空间和具体凭据的哈希，被移除或轮换掉的凭据会使对应 Cookie 失效。

同一密钥下的多台设备共享空间，保留其他设备话题的读取、发消息、审批、回答问题、停止、接管和分叉。话题的 `device` 决定执行设备：A2 向 A1 的话题发送消息，执行仍走 A1 的 SSH door；接管或分叉到 A2 后，后续运行才改走 A2。设备离线、重连、宽限期和运行结果未知的处理继续沿用原逻辑。

## 旧数据

升级前先按原部署方式停服并备份数据。启用多空间后，不可把同一数据目录直接交给不含空间授权的旧版服务；旧版不会检查归属。回退应使用升级前的单空间备份。Docker 镜像与程序包应从包含本改动的同一源码版本构建，既有公开旧镜像不具备该功能。服务首次迁移时，把旧 SQLite/JSON 会话统一归入：

- 保留 `PROXY_TOKEN`：默认归 `default`。
- 只用 JSON 文件：必须用 `PROXY_LEGACY_SPACE_ID` 指明原密钥所在的空间 ID，并在文件中配置该空间。
- 没有原密钥且没有明确归属：旧记录归入不可登录的 `__unassigned__`，保留数据但不可见。不要把第一个连接当作所有者。

归属迁移仅执行一次。后续缺少归属的记录继续不可见，不会被重连、新设备或新密钥认领。已迁移后改变 `PROXY_LEGACY_SPACE_ID` 不重新分配历史。需要修复误配时，由本机管理员停服、从备份核对 `session_spaces` 与 `migrations`；不要在运行中通过普通客户端认领未知记录，也不要随意删除迁移标记。

原生上下文及项目 root 不搬动。迁移保留旧会话和旧项目的 cwd；同设备、同路径的新空间获得独立 root。旧浏览器 Cookie 只有其凭据哈希与空间仍匹配才保留。未知或已无可访问话题归属的调用日志不会通过普通空间查询公开。

## 各种部署方式

Docker/Compose 的镜像、挂载、入口、证书、持久 HOME、升级和备份流程继续使用[部署操作手册](../deploy/README.md)。在已有 `/data/config/service.env` 增加 `PROXY_ACCESS_KEYS_FILE=/data/config/access-keys.json`，把文件保存到宿主数据目录对应的 `config/access-keys.json`，容器沿用原 `/data` 挂载，无须增加端口。只用 JSON 时移除旧 `PROXY_TOKEN`，并设置正确的 `PROXY_LEGACY_SPACE_ID`。`manage.sh token` 仍只管理原 `PROXY_TOKEN`；JSON 内的凭据由管理员编辑私有文件维护。

Linux/macOS 原生进程使用相同配置变量和协议；新增的 macOS 运行方式见[原生服务](native-server.md)。这不替换 Docker，Windows/macOS/Linux 客户端的本机 SSH 执行端也保持原有实现。

Web 默认关闭。多密钥部署由本机管理员在服务配置设置 `PROXY_WEB_ENABLED=1` 开启、`0` 关闭，未设置时保留数据库中的既有选择。Web/手机登录时使用对应空间的服务密钥，Cookie 和 WebSocket 继承该空间。空间内可以查看及撤销自己的已登录浏览器；不能枚举或撤销其他空间的浏览器。全局入口域名、证书、路径和 TOTP 是服务维护设置，不能由普通空间连接修改；复杂公开入口可继续使用原有反向代理配置。

单密钥 Linux 部署保留原来的远程账号和服务管理能力。配置密钥文件后，所有普通空间连接均无共享 Claude 登录/退出、全局 settings/CLAUDE.md 写入、服务安装升级、全局 Web 安全配置权限。共享账号通过服务端本机的官方 CLI 维护，服务版本和 Web 全局设置通过本机配置、原部署工具维护；不引入额外管理账号或角色系统。

## 客户端与权限边界

桌面/Web 的目录、历史、fragment、原生状态、设备、订阅和请求缓存在显式换连接时清空；草稿、项目收藏及项目偏好按服务器地址和空间 ID 分区。临时桥接端口不作为服务器身份。同空间本机窗口仍同步项目收藏；项目有话题后由服务目录在同空间各端可见。

定时任务的 JSON 文件及执行进度也分区。桌面通过当前 SSH 环境中的 `CC_DESK_TUNNEL_SCHEDULES` 指明正确文件；切换空间不会执行上一空间的新话题任务。未标注空间的旧项目收藏、草稿和 `schedules.json` 保留在原处，不自动归入新登录；可由本机用户核对后在目标空间重新添加。旧任务继续话题时仍必须使用话题 ID。

服务在 command 分发之前统一检查话题归属；列表、分页、原生 transcript、PTY 控制、事件广播、调用日志、浏览器登录和 tunnel attach 同样受校验。设备 seat/door 以空间及设备 ID 为索引，跨空间冒用 device ID 不会替换执行通道。多密钥模式的执行通道需要服务访问密钥与临时通道秘密同时匹配；请同步升级桌面/ccdt 客户端。旧单空间客户端的 attach 仍兼容。

本次提供应用资源与连接的授权隔离。Claude Code、终端和服务仍运行于同一受信任的 OS 用户下，原生工具具有该用户的文件权限；这不构成对恶意原生 shell、模型工具或服务宿主管理员的 OS 沙箱。SSH 图片附件仍由话题所属设备的通道读取；没有公开任意文件下载接口。原生终端中直接输入的官方命令也拥有该 OS 用户的权限，管理员应保持原有可信设备前提。

## 离线验收

`spaces.test.ts` 通过真实 WebSocket/HTTP 验证 A1+A2 与 B1 的目录、猜 ID、历史、事件、图片引用、调用日志、审批、停止、迁移、分叉、浏览器登录、撤销、密钥轮换、重启和旧数据归属。`spaces-native.test.mjs` 使用模拟 CLI、官方 SDK、TLS/WSS、桌面桥接与真实 loopback SSH 验证 A2→A1 执行、特殊字符路径、stdin、stderr、退出码及重连通道。它们不调用真实模型，也不使用 Claude 登录命令。
